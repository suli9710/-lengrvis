# 客服、账单与退款运营手册

状态：fail-closed 草案。本文定义付费/公开发布中的客户支持和退款处理。只有 reviewed evidence 通过商业门禁后，本文才可支撑退款、收款或公开支持承诺。

## Case 受理

任何涉及账单、取消、退款、许可证交付或支持承诺的客户 case 都必须记录：

- case ID；
- 收到时间；
- 客户标识的红acted 标签或不透明账户引用；
- 如相关，记录套餐、订阅、发票、激活或许可证引用；
- 问题类别；
- 严重级；
- owner 和备份 owner；
- 下一次更新时间；
- 已采取动作；
- 闭环证据。

不得把卡号、银行信息、原始客户邮箱、许可证 token、激活 key、配对码、诊断包、私有 URL 或本地文件路径复制到 case 备注。

## 账单 case 分类

每个账单/退款 case 使用以下 operator handoff 结构：

```text
客户
- 红acted 客户标签
- 相关账户标识

账单状态
- 有效订阅
- 发票或续费状态
- 异常

决策
- 问题分类
- 为什么该动作正确

已采取动作
- refund / cancel / portal / no-op

客户跟进
- 简短客户消息

产品缺口
- 产品或网站需要修复的内容
```

先分类，再行动：

| Case | 默认动作 |
| --- | --- |
| 个人重复订阅 | 取消重复项；政策允许时退款受影响的重复扣费；保留客户原本想保留的订阅。 |
| 明确的多席位或团队购买 | 保留席位，澄清账单模型，避免误降级。 |
| 失败或未完成 checkout | 先恢复托管门户或开票恢复路径，再判断是否退款。 |
| 缺少自助取消 | 提供门户/取消路径；如客户要求则取消，并记录产品缺口。 |
| 产品失败或信任破裂 | 政策允许时退款受影响费用，记录产品缺陷，并考虑许可证吊销。 |
| 税务或发票争议 | credit 前升级给税务/支付 owner。 |
| 已发起拒付 | 任何退款前先与支付 owner 协调，避免重复损失。 |

## 退款决策矩阵

| 信号 | 决策规则 |
| --- | --- |
| 在已批准退款窗口内 | 除欺诈、拒付冲突或合同例外外，执行退款。 |
| 重复扣费 | 只退重复扣费，不吊销客户本意保留的有效订阅。 |
| Checkout 失败但已扣款 | 根据客户偏好和支付处理方状态，退款或补齐权益交付。 |
| 续费前请求取消 | 取消续费路径，并按政策处理当前 charge。 |
| 产品损坏/价值未达成 | 退款受影响 charge，记录产品问题；订阅结束时吊销付费权益。 |
| 超出政策窗口 | 升级 owner 例外审查；审查前不得承诺结果。 |

退款必须绑定原支付/发票引用或已记录的 credit-note 流程。不得仅凭聊天消息处理退款。

## 退款到许可证吊销

每次退款、拒付损失或行政性付费权益撤销都必须：

1. 确认受影响订阅或发票。
2. 通过不透明引用定位 activation key 或已签发的 `license_id`。
3. 先撤销未来激活或续费。
4. 发布 `docs/business/license-operations.md` 描述的签名吊销 manifest 或替换许可证路径。
5. 确认吊销数据应用后，桌面设置页回退到 Free。
6. 记录客户跟进和对账证据。

离线吊销不是实时的。面向客户的语言必须明确说明这一点；除非该部署已有 reviewed 在线吊销证据，否则不得宣称实时吊销。

## 客户消息

退款已批准：

```text
我们已批准受影响费用的退款。退款将通过原支付路径或已批准的 credit-note 流程退回。该订阅对应的付费权益将按照许可证/吊销流程停止。
```

需要进一步审查：

```text
我们需要先审查账单状态再变更，因为该 case 可能涉及订阅状态、发票/税务处理或既有争议。我们会在 case 约定的下一次更新时间前给出进展。
```

取消已确认：

```text
订阅续费路径已取消。当前访问权限和任何退款资格均以该笔费用适用的已批准政策条款为准。
```
