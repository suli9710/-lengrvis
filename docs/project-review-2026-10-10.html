1. 确认的问题

优先级定义：P1 应优先修复，涉及隐私或关键边界；P2 是特定条件下可触发的功能/可靠性缺陷。下面的三个问题均有隔离复现。发布仪表盘的「P0」属于发布要求的命名，不计入这里的代码缺陷数量。

F01 · P1 · 请求的 privacy 模式在多个模型调用入口丢失

影响：用户明确选择 privacy，仍可能把聊天内容、步骤描述/失败观察、管家目标或偏好文本交给配置的云端模型。

入口和证据：

入口 代码位置 丢失方式
/api/chat 的主管分流 supervisor_agent.py:108 decide(message, mode) 收到 mode，但 get_provider(task="supervisor") 读取全局配置；mode 只进入提示词。
子 Agent 非确定性推理/错误恢复 base.py:96 AgentContext.mode 已存在，选择 provider 时却未使用。编排器调用 agent.act 时也没有注入绑定该任务模式的 provider。
管家保存偏好 butler_conversation.py:263 新建事项保存了 mode，但调用 MemoryAgent.remember 没有传入任务或模式上下文。
管家回忆偏好 butler_conversation.py:281 recall(matter.goal) 同样缺少上下文，查询向量化采用全局设置。

共同触发条件：全局配置仍为 efficiency 并配置云端 provider，而本次请求/任务/事项为 privacy。例如通过 API 为单个请求指定隐私模式，或任务仍保存 privacy、全局配置随后切换。聊天和子 Agent 路径不需要打开文件上传开关；两个记忆路径还需要允许文件内容上传、没有可用本地嵌入实现。回忆路径需要有可检索记忆；常规管家规划还需能到达该步骤。

底层路由器 registry.py:293 本身按传入 settings 正确区分本地和云端。问题是调用方未将请求模式绑定到 settings。MemoryAgent._embed 只在拿到已存在的 task_id 时恢复任务模式；管家事项尚未生成任务时不能依赖此补救。

复现结果： 在独立数据目录、虚构文本和占位密钥下，拦截实际云端 provider 方法，handle_chat(..., "privacy") 和 BaseAgent.act(context.mode="privacy") 都选择了 efficiency provider，且消息包含测试标记。两条记忆路径的实际 /embeddings 请求参数包含隐私目标/偏好。拦截在网络发送前完成，没有实际上传文本。证据：privacy-routing.log、复现程序。

修复建议： 统一构造绑定请求/任务/事项 mode 的 settings，并传给所有 provider 和 embedding 调用。为没有 task_id 的管家会话提供显式模式参数。不要只修改提示词或只修 planner。增加「全局 efficiency + 请求 privacy」的端到端调用边界测试，断言云端调用次数为零；本地模型不可用时按现有隐私策略失败或使用明确允许的本地降级。

F02 · P2 · 手机前后台切换可能重复使用刷新令牌，撤销整个会话

位置：mobile/app/_layout.tsx:98、定时刷新:175、效果清理:201。

触发顺序： 定时刷新已发出、响应仍在途中 → 手机进入后台，清理 effect → 快速返回前台，加载 SecureStore 中尚未替换的旧会话 → 前台初始化再次发送相同 refresh token。effect 的 active=false 只影响后续 UI 提交，不能收回已经发出的刷新请求。replaceSessionIfTokenMatches 发生在网络请求之后，也不能阻止两次令牌轮换。

后端 mobile_identity.py:199 将第二次使用已经 rotated 的令牌判定为重放，并撤销 token family。因此第一次请求刚换得的 access token 也变为无效，用户需要重新配对。

复现结果： 从实际 RootLayout 文件提取并执行两个 effect，配合真实移动端 API client 和受控网络延迟，得到 request_count=2、same_refresh_token=true。再用独立数据库中的真实后端轮换逻辑验证：第二次刷新返回 401，第一次的新 access token 也返回 401，family 状态为 compromised。这是受控生命周期复现，不是 Android 真机测试。证据：mobile-race.log、复现程序、后端证据。

修复建议： 将刷新和持久化放入跨 effect 生命周期的单一会话管理器，同一会话共享进行中的刷新 Promise，直到新令牌安全写入后才允许下一次刷新。保留服务端的重放防护。增加「请求进行中切后台/切前台」及退出、重新配对与刷新并发的测试。

F03 · P2 · Office 完成条件把输入文件类型加入必需输出

位置：butler_office_completion.py:33、必需输出合并:68。

触发示例： 用户说「读取现有 Excel 数据，生成 Word 报告」，结构化完成条件也只声明 artifact_kinds=["docx"]。当前逻辑根据目标中出现的 Excel/Word 名称直接补充输出要求，得到 {docx, xlsx}，没有区分输入材料与交付物。

即使事项已经记录 Word 成果，verify_office_completion:85 也会先返回「仍需完成请求中的 Excel 成果」。后续协调会进入未完成处理，可能额外规划或创建用户未要求的表格，或停留在无法完成状态。

复现结果： 中文和英文等价目标均错误要求两个格式；加入只有 docx 的成果记录后，校验在文件完整性检查之前就以缺少 Excel 为由拒绝。该复现验证的是错误的完成条件，并未声称生成或打开了真实 Office 文档。证据：privacy-routing.log、复现程序。

修复建议： 让明确的输出契约主导完成判定；从用户意图补充契约时区分读取/引用的输入与生成/导出的输出，后续明确变更仍需生效。加入「Excel 输入 → Word 输出」「Word 输入 → Excel 输出」「双输出」「明确不打开」的回归用例。
