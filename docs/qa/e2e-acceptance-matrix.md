# Lengrvis End-to-End QA Acceptance Matrix

Last reviewed: 2026-06-08

This matrix defines the release-facing QA coverage for Lengrvis across backend, desktop, and mobile. A release candidate should not ship until every P0/P1 row is either passing with recorded evidence or explicitly waived in the release notes with an owner and follow-up. P2/P3 rows keep optional, platform-specific, and demo-polish risk visible without turning every release into a full-platform certification run.

## Gate Levels

| Level | Meaning | Release expectation |
| --- | --- | --- |
| P0 | Core safety, launch, packaging, or data-protection behavior | Must pass for every release candidate. |
| P1 | Primary user journey or cross-device workflow | Must pass unless the release intentionally excludes that surface. |
| P2 | Important regression coverage for optional or environment-specific capabilities | Run when the feature, platform, or dependency is touched. |
| P3 | Demo polish, observability, documentation, or nice-to-have workflows | Run before stakeholder demos or when touched; track gaps as residual risk. |

## Evidence Checklist

- Record the exact command, date, commit, platform, and result for each automated gate.
- Attach screenshots or short notes only for manual P1/P2/P3 checks that are not already covered by automated logs.
- Record local model readiness/smoke, Skill sample, mobile companion, document citation, and template demo evidence whenever those capabilities are mentioned in demo material or release notes.
- For Windows release candidates, record `npm run release:check` exit status, source-map artifact policy result, structural packaging verification, and runnable backend smoke; attach `.tmp\packaging-smoke` logs only when the smoke fails or times out.
- Record packaged portable GUI task evidence separately from portable launcher/backend diagnostics; a visible window plus `/health` is not proof that a user launched a task from the GUI. Record read-only entry pass, natural-language pass, natural-language unsupported, and blocked artifacts as separate states.
- For diagnostics/product-metrics claims, record the diagnostics test command and whether any package was exported from UI or API; do not imply cloud telemetry, long-term trend analytics, or shareable full-path redaction unless separate evidence exists.
- For Skill Product Manifest claims, record whether evidence comes from manifest-declared permissions or inferred UI signals, and whether it is backend/source-level, mocked DOM/screenshot, or real release-candidate import evidence. Inferred signals are risk hints, not authoritative permission boundaries.
- For mobile/LAN claims, record the scheme, host, real phone/emulator path, camera/QR evidence, and explicit certificate trust path. Non-loopback HTTP LAN is blocked for token-bearing mobile flows; use it only as blocked-path evidence, not as a demo pass.
- For Settings local-model claims, record whether evidence is backend/API, mocked Vite DOM, clean-machine install/start, or visual layout review; do not count a DOM assertion as proof that the beginner-facing layout is polished at common desktop widths.
- Treat missing dependencies, absent artifacts, or skipped platform checks as "blocked", not "passed".
- Any waiver must include an owner, user impact, expiry condition, and a follow-up issue or task.
- P0 failures are stop-ship; P1 failures require an explicit release exclusion or waiver; P2/P3 failures become residual risks unless the touched feature or demo depends on them.
