# Lengrvis Agentic Product Evals

Last reviewed: 2026-06-08

This file tracks the eval-first operating contract for the multi-agent productization push. The goal is to make Lengrvis feel safe, capable, and ready for a first-time user without turning the UI into a developer console.

## Product Bar

Lengrvis should be judged against OS-agent products such as Marvis, Copilot-style local assistants, ChatGPT Agent/Operator, and self-hosted agent workbenches. It does not need to copy their surface area; it needs to win on a clear lane:

- Local-first OS agent that can finish useful computer tasks.
- Safety review, dry-run approval, rollback, and audit trail for state-changing work.
- Simple first-run experience for non-technical users.
- Mobile companion flows that do not require users to understand IP addresses, ports, or WebSocket details.
- Repeatable release evidence instead of demo-only confidence.

## First-Round Completion Criteria

The first productization round is complete only when these checks are true or explicitly waived in the QA handoff:

| Area | Eval | Pass signal |
| --- | --- | --- |
| First win | A fresh user can start one local read-only task from the first screen. | Task reaches visible progress and either completes or fails with actionable next steps. |
| Behavior smoke | Mobile pairing and remote-input smoke prove real request/response behavior. | Smoke scripts exercise HTTP/WS contracts or a self-contained local behavior stub, not only source regex checks. |
| Safe actions | R2/R3 actions require preview and approval; R4 stays blocked. | Backend tests and demo gate include one approved reversible action and one blocked forbidden request. |
| Mobile pairing | Pairing supports a QR/pair payload path and classified failures. | UI distinguishes bad address, backend not reachable, expired code, and permission denial. |
| Diagnostics | Desktop exposes version, backend status, logs, and exportable diagnostics. | A user can produce a support bundle or clear diagnostic evidence without browsing repo folders. |
| Release readiness | Release gate proves runnable artifacts. | `npm run release:check` or an equivalent command runs executable smoke, not only file existence checks. |

## Review Rules

- Do not count a capability as done because a code path exists; count it when a user-facing flow or automated gate proves it.
- Keep UI controls novice-friendly: one primary action, clear status, and failure text that tells the user what to do next.
- Treat safety and privacy regressions as stop-ship even when the product demo looks good.
- Prefer small, independently verifiable changes over broad refactors.
- Record any waiver with owner, reason, expiry condition, and follow-up task.
